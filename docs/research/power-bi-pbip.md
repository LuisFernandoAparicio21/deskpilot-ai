# Power BI report as code (PBIP/PBIR/TMDL, REST) vs building by hand

Consulted: 2026-11-22. Branch chore/phase-c-plan. Extends `power-bi-fabric-connection.md` (manual connection and licenses).

## Question
Can a Power BI report connected to the Fabric lakehouse be generated by code (PBIP with PBIR and TMDL, the auto-generated default report, or `fab`/REST creating semantic model and report), or is it safer to ship DAX measures plus a page design and build it by hand in Power BI Desktop or the Fabric service? Which license is needed to publish/share versus only taking screenshots from Desktop?

## Answer
- **PBIP is code-friendly.** Saving as a Power BI Project writes the semantic model and the report as plain-text folders (`<name>.SemanticModel` with TMDL under `definition/`, `<name>.Report` with `definition.pbir` and the PBIR `definition/` folder). Microsoft says you can generate and edit these files programmatically. Desktop detects external edits and offers to apply them.
- **Fragile parts.** Editing outside Desktop can cause errors or stop Desktop from opening the project. Files with undocumented schema must not be edited outside Desktop: `report.json` (the PBIR-Legacy file), `mobileState.json`, `diagramLayout.json`. The PBIR `definition/` folder has JSON schemas (page.json, visual.json). Which Desktop build makes PBIR the default, and whether PBIR is still labeled preview: ⚠ not confirmed in the cited pages. PBIX to PBIP cannot be converted programmatically (Desktop Save as only).
- **Fabric REST** can create a report from a definition: parts `definition.pbir` (required, holds the semantic model reference, `byConnection` with `semanticmodelid=...`), plus `definition/` parts (`report.json`, `version.json`, `pages/.../page.json`, `visuals/.../visual.json`) sent as base64 (`InlineBase64`). Deploy options for a PBIP: Fabric Git integration, Fabric APIs, or Desktop Publish. `fab` (Fabric CLI) importing a PBIP folder: ⚠ not confirmed (not in these pages).
- **Semantic model**: since 2025-09-05 the default semantic model is NOT created automatically for a lakehouse, warehouse or mirrored item, so the "auto-generated default report" path starts with creating a semantic model manually (service: Create semantic model; semantic models are independent REST-manageable items). The "Auto-create a report" button exists in the service UI but still needs a semantic model first and gives a generic layout.
- **Conclusion on effort/risk**: generating a full report by code is possible but costly: hand-writing `visual.json` is verbose, the model must exist first, and no end-to-end generation was tested here (⚠ not confirmed). Verify any generated project by opening it in Desktop.
- **License** (from the previous research page, plus semantic-model page): screenshots from Desktop need only the free Desktop plus an Entra account with workspace access (⚠ Pro not needed: not explicit in sources). Publishing/sharing outside My workspace needs Pro or PPU (or an individual trial); with F64 or Trial capacity, Free users with Viewer role can view; Direct Lake live edit does not work with a Free license.

## Recommended decision
For the portfolio demo, do not generate the report by code. Deliver in the repo: (1) the DAX measures as text, (2) a page design (visual list per page, fields, filters), and (3) optionally a small TMDL semantic model file. Build the report by hand in Power BI Desktop (Import via SQL analytics endpoint), save as PBIP so the text files can be committed (short root path, UTF-8 without BOM, Windows 260-char limit), and take screenshots for `docs/screenshots/`. Try REST/PBIR generation only as a stretch goal, validated by opening in Desktop.
